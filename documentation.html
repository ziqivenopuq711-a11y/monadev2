Getting Started

Deploy Your First Contract in 5 Minutes

Monad is fully EVM-equivalent. If you can deploy to Ethereum, you can deploy to Monad — the only change is the RPC URL and chain ID.

  1. Install Foundry

    Foundry is the recommended toolkit for Monad development. Install it with the official installer:

    curl -L https://foundry.paradigm.xyz | bash
foundryup

  2. Create a New Project

    Initialise a new Foundry project and open the default counter contract:

    forge init my-monad-project
cd my-monad-project

  3. Get Testnet MON Tokens

    Visit the Monad faucet at faucet.monad.xyz, connect your wallet, and claim test MON to pay for gas on the Monad Testnet.

  4. Deploy to Monad Testnet

    Use Foundry's forge create to deploy. Replace YOUR_PRIVATE_KEY with your deployer key:

    forge create src/Counter.sol:Counter \
  --rpc-url https://rpc.monad.xyz/testnet \
  --private-key YOUR_PRIVATE_KEY \
  --broadcast

  5. Verify on the Explorer

    Confirm your deployment was successful by searching for your contract address on Monad Explorer. Verify the source code so others can audit and interact with it.

Core Concepts

Architecture Overview

Understanding how Monad works under the hood helps you write more efficient contracts and anticipate how your application will behave at scale. There are three core systems to understand: the consensus layer (MonadBFT), the execution layer (the parallel EVM), and the storage layer (MonadDB).

MonadBFT — Consensus Layer

MonadBFT is a pipelined, Byzantine Fault Tolerant consensus protocol derived from HotStuff. It operates in a leader-rotation model where a designated proposer broadcasts a block, validators cast signed votes, and the block is committed once a two-thirds quorum is reached. The critical innovation is that MonadBFT decouples consensus from execution — validators commit to the order of transactions, not to their execution results. This allows a new consensus round to begin immediately after the previous block is ordered, rather than waiting for execution to complete. The result is ~400–500 ms block times and approximately 800 ms finality.

Optimistic Parallel EVM — Execution Layer

Once the order of a block is finalised by MonadBFT, the execution engine processes all transactions in that block simultaneously across available CPU cores. Each transaction's memory access is tracked in a read-set and write-set. After the parallel phase, a serial validation pass checks each result in block order: if a transaction's read-set is unchanged by all transactions committed before it, the result is applied; if a conflict is detected, the transaction is re-executed serially to produce the correct result. This optimistic model avoids all re-execution overhead for conflict-free transactions — the vast majority in typical workloads — while guaranteeing deterministic correctness identical to sequential execution.

MonadDB — Storage Layer

MonadDB is a custom embedded database designed specifically for blockchain state. Unlike Ethereum's approach of layering a Merkle-Patricia Trie over a generic key-value store (LevelDB or RocksDB), MonadDB implements the trie natively within its storage engine. This eliminates one level of indirection on every state access, reduces memory pressure by keeping less data in RAM, and allows concurrent reads and writes from multiple threads — crucial for the parallel EVM above it. MonadDB also supports efficient state snapshots for fast node synchronisation without full historical replay.

Key implication for smart contract developers: Monad executes transactions in parallel, but the committed result is always equivalent to a serial execution in block order. Your contract logic does not need to account for parallelism — write Solidity as you always have.

RaptorCast — Network Propagation

Monad uses RaptorCast, an erasure-coding-based gossip protocol, to propagate blocks across the validator network efficiently. RaptorCast splits each block into coded fragments and distributes them such that any node can reconstruct the full block from a subset of fragments. This dramatically reduces the bandwidth required per validator and speeds up block propagation, a critical factor in achieving sub-second finality at scale.

API Reference

JSON-RPC API

Monad implements the full Ethereum JSON-RPC specification. All standard eth_*, net_*, and web3_* methods are supported. The following table highlights the most commonly used endpoints.

MethodDescriptionCategory
eth_blockNumberReturns the current block numberBlock
eth_getBlockByHashReturns block data for a given hashBlock
eth_getTransactionByHashReturns transaction data for a given hashTx
eth_getTransactionReceiptReturns the receipt of a mined transactionTx
eth_sendRawTransactionSubmits a signed transaction to the mempoolTx
eth_callExecutes a call without creating a transactionState
eth_estimateGasReturns an estimate of the gas needed for a transactionGas
eth_getLogsReturns logs matching a filter objectEvents
debug_traceTransactionReturns an opcode-level execution traceDebug

Example: Get the Latest Block

curl https://rpc.monad.xyz/testnet \
  -X POST \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "method": "eth_getBlockByNumber",
    "params": ["latest", false],
    "id": 1
  }'
