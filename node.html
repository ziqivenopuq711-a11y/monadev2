Run a Monad Node

Participate in securing the Monad network by running a validator or RPC node. Monad's MonadDB state engine is specifically designed to keep hardware requirements accessible — fast NVMe SSD and moderate RAM are sufficient for a full node.

Hardware Requirements → Installation Guide
Node Types

Choose Your Role in the Network

🔒

Validator Node

Validator nodes participate in MonadBFT consensus — proposing blocks, casting votes, and earning MON staking rewards. Running a validator requires meeting the minimum self-stake requirement and maintaining high uptime. Validators are accountable for their performance through the slashing mechanism.

  • Earns MON staking rewards
  • Participates in block production
  • Requires minimum stake deposit
  • Subject to slashing for misbehaviour
📡

RPC / Full Node

Full nodes keep a complete copy of the Monad chain state and serve JSON-RPC requests. Running an RPC node is permissionless — no stake required. RPC nodes are essential for dApp backends, wallets, indexers, and anyone wanting a trusted, self-hosted endpoint to query chain state.

  • No stake requirement
  • Serves eth_* JSON-RPC calls
  • Supports archive mode for full history
  • Ideal for dApp backends
Infrastructure

Hardware Requirements

MonadDB's efficient state storage means Monad nodes can run on commodity server hardware without the extreme RAM requirements of some high-throughput chains.

🏅 Recommended (Validator)

CPU16-core / 32-thread (x86-64)
RAM32 GB DDR5
Storage2 TB NVMe SSD (PCIe 4.0)
Network1 Gbps dedicated
OSUbuntu 22.04 LTS
Uptime> 99.5% required

💻 Minimum (RPC Node)

CPU8-core x86-64
RAM16 GB DDR4
Storage1 TB NVMe SSD
Network500 Mbps
OSUbuntu 20.04+ / Debian 11+
UptimeBest-effort

Why lower RAM than comparable chains? MonadDB stores the majority of state on NVMe SSD with an intelligent caching layer, rather than requiring the full state trie in memory. This design choice is intentional — broader hardware accessibility means more validators, which means greater decentralization.

Setup Guide

Installing and Running a Monad Node

The following steps guide you through setting up a Monad full node on Ubuntu 22.04 LTS. The process covers prerequisite installation, downloading the Monad node binary, configuring the node, syncing the chain, and starting the node as a managed system service.

  1. System Prerequisites

    Update your system packages and install required build tools:

    sudo apt update && sudo apt upgrade -y
sudo apt install -y curl wget git build-essential \
  libssl-dev pkg-config jq

  2. Download the Monad Binary

    Download the latest pre-built Monad binary for your architecture:

    curl -LO https://releases.monad.xyz/monad-node-linux-amd64.tar.gz
tar -xzf monad-node-linux-amd64.tar.gz
sudo mv monad-node /usr/local/bin/
monad-node --version

  3. Configure the Node

    Initialise the node data directory and edit the configuration file:

    monad-node init --network testnet --datadir ~/.monad
# Edit config at ~/.monad/config/config.toml
# Set your external IP, p2p port, and RPC settings

  4. Download the Genesis Snapshot

    Sync from a state snapshot to avoid replaying the entire chain history from genesis (recommended for testnet):

    monad-node snapshot restore \
  --url https://snapshots.monad.xyz/testnet/latest.tar.lz4 \
  --datadir ~/.monad

  5. Create a systemd Service

    Run the node as a managed background service so it auto-restarts on failure or reboot:

    sudo tee /etc/systemd/system/monad-node.service > /dev/null << EOF
[Unit]
Description=Monad Node
After=network.target

[Service]
User=$USER
ExecStart=/usr/local/bin/monad-node start --datadir ~/.monad
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable monad-node
sudo systemctl start monad-node

  6. Verify the Node is Running

    Check the service logs to confirm your node is syncing and connected to peers:

    journalctl -u monad-node -f --no-pager
# Look for: "Syncing blocks" and "Connected to N peers"
Operations

Monitoring & Maintenance

A healthy node requires ongoing monitoring to ensure it stays in sync, maintains peer connections, and responds to network upgrades promptly. The Monad node binary exposes a Prometheus metrics endpoint for integration with standard observability stacks.

Prometheus Metrics

Enable the metrics endpoint in config.toml to expose performance and health metrics:

[metrics]
enabled = true
host = "0.0.0.0"
port = 9090

Key metrics to monitor include:

  • monad_chain_head_block — current chain head; should increase every ~500 ms
  • monad_p2p_peers — number of connected peers; healthy nodes maintain 20–50
  • monad_db_read_latency_ms — MonadDB read latency; spikes indicate storage I/O issues
  • monad_execution_tps — current transaction processing rate

Software Upgrades

Monad releases mandatory protocol upgrades as the network evolves toward mainnet. Subscribe to the Monad Discord #node-announcements channel for upgrade notices. Upgrades typically require stopping the service, downloading the new binary, and restarting — all existing data and configuration is preserved.

Troubleshooting

The most common node issues are: insufficient peers (check firewall rules, ensure TCP port 30303 is open), state database corruption after an unclean shutdown (run monad-node db repair), and RPC timeouts under high load (increase rpc.max_threads in config). The Monad documentation and Discord #node-support channel cover additional edge cases.
